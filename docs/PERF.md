> 测试日期：2026-10-24
> 基线：main `f85ea11`
> 构建：Windows release（`flutter build windows --release`）

| 项 | 值 |

## 测试数据

- **10,000 首 FLAC**，总大小 81 MB
- 每首 0.25 秒、44.1 kHz、单声道，仅用于压测，不含真实音乐
- 500 张专辑（每张 20 首）、137 位艺术家、曲目号 1–20
- 每首内嵌同一张 8×8 PNG（用于触发封面提取；内容哈希去重后只落 1 个文件）
- 生成脚本使用 Python `soundfile` + `mutagen`，仅本地执行，不随仓库提交

## 方法

测量入口是临时探针，直接调用 Rust API，不经过界面：

- **冷扫描**：空库对 10k 目录执行一次 `scanFolder`
- **热扫描**：紧接着再执行一次，验证增量跳过
- `allTracks`：一次全量读取 10,000 条
- `searchTracks`：4 个查询（精确曲名、艺术家、专辑、数字前缀），limit 500
- 数据库体积：关闭连接后统计 `library.db` + `-wal` + `-shm`
- **列表滚动**：release 应用加载 10k 曲库，向曲库列表发送 180 次滚轮事件，
  用 `SchedulerBinding.addTimingsCallback` 统计每帧 `build + raster` 耗时

## 解读

- 冷扫描约 **1.0 ms/首**，主要开销在文件 IO、FLAC 解码和封面提取；10k 首次导入约 10 秒
- 热扫描 **0.23 秒**，增量指纹生效，没有重复解析
- `allTracks` 20 ms、搜索 0–2 ms，曲库规模到 1 万条时查询侧没有压力
- 列表用 `ListView.builder` + `itemExtent` 虚拟滚动，滚动帧耗时 P95 7 ms，
  没有掉帧，满足 60 FPS
- 数据库 10k 条约 3 MB，体积正常

## 注意事项

- 压测文件只有 0.25 秒且共用一张 8×8 封面，因此冷扫描偏乐观、封面缓存极小；
  真实曲库的封面各不相同，缓存体积会明显增加，但去重逻辑已由 Rust 测试覆盖
- 以上为 release 数据；debug 构建下冷扫描约 11.5 秒、`allTracks` 约 95 ms，
  不作为验收口径
- 10k 曲库放在仓库外的 `D:\lamp-perf-library`，不进入版本库

## 帧耗时类测量的前提（2026-11-01 踩到过）

用 `FrameTiming`（`tool/hero_flight_bench.dart` 之类）量渲染开销时，**窗口必须在前台**：
窗口被遮挡或最小化时 Windows 不合成，`rasterDuration` 会给出 0.3 ms 这种「好看但没有
意义」的数字，据此下结论会南辕北辙。基准脚本自己的启动段要抢前台：

```dart
await windowManager.waitUntilReadyToShow(options, () async {
  await windowManager.show();
  await windowManager.focus();
  await windowManager.setAlwaysOnTop(true);
});
```

`flutter run` 拉起的窗口不一定会被系统切到前台，`--release` 下尤其容易被忽略。

配套结论：**封面 Hero 飞行带阴影与不带阴影的 raster 在同一量级**（均 0.3 ms、P95 0.4，
240 Hz 屏）。这份基准是裸页面（只有两个大方块，没有歌词 / 频谱 / 流光背景），绝对值不能
拿去和整页数字比，只用于比较两组之间的差额：阴影在 shuttle 里按固定尺寸光栅化一次、
之后每帧只改 `Transform` 矩阵，所以「boxShadow 每帧重做高斯模糊」的代价只在
「每帧按新尺寸重画」时才存在，固定尺寸缩放几乎不花钱。

## 扫描并行化（2026-11-14）

改动前 `scanner::collect_tracks_incremental` 把「walkdir 遍历」和「lofty 解析 + 封面
归一化」放在同一个循环里，逐文件串行。拆成两段：遍历只取 mtime / 大小，待解析文件
按块分给线程池（`available_parallelism()`，上限 8），结果按候选顺序合并。

测量用临时 example（`scanner::collect_tracks_incremental`，含封面提取，不含入库），
本机 101 首真实曲库（3.2 GB，FLAC / MP3 混合），每档跑 3 轮取稳定值：

| 线程数 | 耗时 | 单文件 |
| --- | --- | --- |
| 1（串行） | 6.9–7.0 s | 68–70 ms |
| 4 | 2.3–2.7 s | 23–27 ms |
| 8 | 1.3–1.5 s | 13–15 ms |

再往上收益很小，而封面归一化每线程都要解一张原图（3000px 瞬时几十 MB），
所以上限取 8，核数少的机器按实际核数降。

两个实现要点：

- 外挂封面缓存原来是 `&mut HashMap`，并行后改成 `Mutex`；**读盘必须放在锁外**，
  否则一张 8 MB 的外挂图会把其它线程全堵在锁上。同一目录并发首次命中最多各读一遍，
  内容哈希落盘的结果相同
- 遍历阶段的 `known` 指纹表只在单线程里读，不需要共享；`seen` 与计数也留在遍历段，
  线程池只返回（曲目, 失败数）

注意：`PROBE` 类基准测的是解析段，入库仍是单事务，整体冷扫收益略小于上表。

### 这次量出来的问题：扫描前逐曲目查封面

v10 起每次扫描前都会跑 `tracks_with_missing_covers()`：把封面文件已经不在的曲目
指纹抹掉、强制重解析（封面缓存被清、曲库搬家的兜底）。原实现是「每首曲目
`fs::metadata` 一次封面」，而同一张专辑封面通常被二十首共用——1 万首曲库上这段实测
**2.44 s**，全花在重复的同一批路径上（Windows 上 `metadata` 要开句柄，被杀软拦一次
就 0.2 ms 起）。

改成按封面路径去重再查盘（`collect_missing_covers`，`HashMap` 记住每个封面查过的
结论），同一张封面只查一次：**2.44 s → 7 ms**，热扫描整体 5.14 s → 0.36 s。
覆盖用例 `missing_covers_dedupes_by_cover_path` 直接断言「一万首共用一张封面只查一次
盘」「缺封面 / 有封面混在一起时只返回缺的那些」。

### 解读

- 冷扫描 0.69 ms/首，比 10 月的 1.0 ms/首更快，并行解析 + 入库 SQL 都吃到收益
- 增量扫描修完是 **0.36 s / 10k**，加目录、启动补扫这类操作不会再卡在「什么都没变」
  的等待上
- v10 老库补扫 7.84 s 是一次性的：它在重解析全部曲目（含封面复核），之后走增量
- 搜索 6–10 ms 比上次的 0–2 ms 慢，是这次的场景带了 `limit 500` 与更宽的列；
  绝对值仍是「点一下就有」的量级，不是瓶颈
- 列表滚动 release 下 P95 5.25 ms、没有掉帧，和 10 月基线（P95 7 ms）一致
